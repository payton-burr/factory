# Bigpowers → Atomic integration assessment (synthesis)

Research and recommendations only. Nothing was installed, enabled, configured, committed, or executed from upstream; the only source access was read-only file reads and one `git rev-parse` in the pinned checkout. Upstream skill text was treated as evidence, not instructions. Upstream `model:`/`effort:` pins were ignored throughout.

## 1. Executive summary

**Do not install Bigpowers 2.88.2 or enable `extensions/omp-hooks.ts`. Adopt its methods selectively through Atomic-native mechanisms, with one runtime state owner, explicit delivery authority, and no duplicate slash-command surfaces.**

- **Inventory:** 81 canonical `skills/*/SKILL.md` at commit `cbff374ee2d4095b53a81696262a39f164fa0774` (80 active + 1 tombstone, `define-success`). `.pi/skills` and `.pi/prompts` are generated mirrors (81 each), not extra skills. The manifest's "73", `README.md#L191`'s "80", and `scripts/mcp-server.js#L2`'s "68" are stale hand-written counts; `README.md#L5`'s "81" badge is stamped by `scripts/lib/sync-post.sh:90` (integration.md §1). All 81 carry `model:` pins (25 haiku / 49 sonnet / 7 opus, verified by grep) and 75 of 81 open with "HARD GATE" absolutes; both are excluded from the recommendation.
- **Primary classification (81/81):** 52 skill, 14 workflow, 9 prompt-template, 4 subagent, 2 extension. This is a classification of *responsibilities*, not a resource count: the 14 workflow-primary skills collapse into **three workflow definitions** (planning; verified implementation with story/plan/bug modes; separately authorized delivery), one optional coordinator, and one deferred maintenance workflow. The 9 template-primary skills reduce to at most 4 actual templates. The 4 subagent-primary skills need at most 2 new agent definitions (investigation-only debugger variant, independent security reviewer); the other two reuse bundled analyzers/research agents. The 2 extension-primary skills are both gated: `guard-git` is a user decision (confirm vs block vs none), `visual-dashboard` is deferred behind native workflow status.
- **Adoption disposition:** 50 adapt, 14 replace-with-native (Atomic already owns the capability; keep at most a reference note), 10 defer (blocked on invalid tooling or missing dependencies), 6 decision-gated (external mutation or policy choice), 1 alias-only.
- **Hard blockers found in source (static findings, not reproduced runs):** the benchmark runner fabricates its "no-skill" control and accepts nonzero graders that print PASS (R1); "dry-run" publishing uploads to TestPyPI (E); the CI waiter and land-branch scripts can report success without CI evidence and force-remove worktrees (F); the git guard blocks the user's own `commit-work` heredoc commits and every commit on `main` while being bypassable by `git commit -F` (integration.md §3); `skills-lock.json` paths are malformed so the legacy MCP server cannot resolve any skill; `bigpowers_skill run` returns a false `injected: true` receipt under Atomic's fire-and-forget `sendUserMessage` (integration.md §2).
- **Model policy:** skills and templates carry no model. Executable roles use the contract's configured subset with same-role, other-family fallback at the same supported level; details and dated evidence in §7. No numbers were refreshed live.
- **One correction to a source report, resolved from upstream source:** `delegate-task` moves from workflow (skills-b.md) to **skill**; its dispatch/retry/acceptance loop is the native `subagent` tool plus `goal`/`ralph` review-repair, and only its brief template and two-stage checklist are new knowledge (`skills/delegate-task/SKILL.md#L18-L45,#L47-L90`). Partition totals were 51/15/9/4/2; the synthesized totals are 52/14/9/4/2.

## 3. Mechanism boundaries applied

| Mechanism | Owns | Does not own |
|---|---|---|
| Skill | Reusable method/knowledge, progressively loaded; `/skill:name` and system-prompt catalog are the model surface (`docs/skills.md:33-81,105-149`) | Tools, permissions, delegation authority, model choice (`docs/skills/reference.md:56`) |
| Prompt template | Explicit user shortcut with `$ARGUMENTS` (`docs/prompt-templates.md:5-19,69-79`) | Scheduling, policy, model changes |
| Subagent | Bounded, non-interactive specialist with fresh context; model/fallback lives on the agent definition (`docs/subagents.md:8-10,49-55,206-208`) | User questions, scope changes, consequential decisions |
| Workflow | Durable order, dependencies, artifacts, checkpoints, human gates, bounded acyclic remediation (`docs/workflows/authoring.md:161-171,218-233,501-507`) | Methods (those come from skills) |
| Extension | Actual event interception, custom tools, UI (`docs/extensions/events.md:510-527,630-675,712-789`) | Anything expressible as a workflow stage or skill |

Rule from `docs/build.md:11-19`: stop at the lightest mechanism.

## 8. State, gates, authority, portability, security, licensing

**State ownership (contract item 5).** `specs/state.yaml` is upstream's single source of truth with a mandated `handoff.next_skill` routing channel (`up:CONVENTIONS.md#L158-L204`, `up:specs/state.yaml#L1-L40`). Field forms are inconsistent across skills (`active_epic` vs `active_epic_id`, `step` vs `current_step`, numeric vs skill-name counters, `completed_steps` as text or array; skills-a.md "One execution-state owner"). `sync-status-from-epics.sh` seeds missing keys with `setdefault`; it is not a reconciler (R3). Timing instrumentation does whole-file read/modify/write on shared state (R8). **Decision, not silent adoption:** Atomic's workflow runtime owns execution state; project documents own requirements/ADRs; any `state.yaml` export is an advisory projection with one writer; an extension that watches `next_skill` and launches work is explicitly rejected.

**BCP and quality gates.** BCP is element-based scoring with calibration identity and explicit non-time semantics (`up:docs/references/bcp.md#L9-L64`, `up:docs/references/bcp-plus.md#L132-L151,#L207-L223`); `slice-tasks` uses a 1-13 shortcut instead. The 94% threshold counts repository Gherkin scenarios (`up:docs/PRINCIPLES.md#L67-L71`) and is reused for subjective review scores in `request-review`. Neither should become an Atomic default. Require: observable acceptance criteria, executable checks as tool nodes, independent findings, explicitly authorized waivers.

**Approval/release/merge authority.** `release-branch` chains readiness → `gh pr create` → `gh pr merge --squash --delete-branch` or `land-branch.sh` squash+push to main (`up:skills/release-branch/SKILL.md#L23-L36,#L75-L119`; `up:scripts/land-branch.sh#L100-L165,#L195-L206`); `wait-for-ci.sh` can exit zero without `gh` and treats cancelled/timed-out runs as non-failure (`up:scripts/wait-for-ci.sh#L40-L111`); the push fallback can reset the local default branch (`up:scripts/lib/land-branch-push.sh#L39-L105`). `publish-package` "dry-run" uploads to TestPyPI and offers `--no-verify` (`up:skills/publish-package/REFERENCE.md#L24-L31,#L249-L259`). **Recommendation:** completion establishes "ready for integration"; every external action is a separate human-input gate.

**Unsafe defaults / conflicts with Atomic and global instructions.**
- Automatic git actions (`chore(state)` commits, squash-merge, push to main, semantic-release) conflict with the no-automatic-git posture and with the factory repo's single-commit `main`.
- Guard blocks the user's `commit-work` heredoc form and every commit on `main`, is bypassable via `git commit -F`, `git push origin HEAD:refs/heads/main`, `sh -c`; upstream's shell hook exempts itself via `GIT_BIGPOWERS_LAND=1` (`up:hooks/pre-tool-use.sh#L8,#L25`; `up:scripts/land-branch.sh#L148`); false positives on `git checkout ./src`, `git clean -fdn` (integration.md §3).
- `CHANGELOG.md` is generated by `@semantic-release/changelog` (`up:.releaserc.json`); `publish-package/REFERENCE.md#L100-L117` advises editing it - conflicts with the read-only rule. Atomic's `write` refuses generated-looking files (`docs/tools.md:88`).
